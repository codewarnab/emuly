Emuly link plan

How an app on an Emuly phone connects to a server that is on the laptop of the user. Status: built (steps 1 to 5). Step 0, a test of gh codespace ssh -R on a real phone, is not done.

1. The problem

The app runs in an emulator. The emulator runs in a GitHub codespace. The server runs on the laptop.

The codespace cannot open a connection to the laptop. The laptop is behind a home or office router.

The repo has no path from the emulator out to the laptop today. All connections go inward: control plane, then runner, then emulator.

2. The solution: a link

A link is a tunnel for one TCP port from the phone to the laptop. The agent starts a link with one command:

emuly link <phone> 3000

After that, the app calls localhost:3000 or 10.0.2.2:3000. The user does nothing.

The laptop always opens the connection outward. The router of the user permits that.

A link is raw TCP. HTTP, websocket, gRPC, and the Metro bundler on 8081 all work. UDP does not work.

The rule of the shortest path

The agent uses a link only when the server needs one. This keeps each request fast.

Where the server isWhat the agent doesPath of a request
Public internetNothingPhone, then internet
Inside the codespaceNothing. The app uses 10.0.2.2:<port>.Phone, then codespace
Laptop localhostemuly link <phone> 3000Phone, codespace, tunnel, laptop
A machine that the laptop can reach: LAN, VM, Tailscaleemuly link <phone> 8080 --to <host>:8080Phone, codespace, tunnel, laptop, that machine

The last row covers Tailscale. The laptop is already on the Tailscale network, so the laptop relays the traffic.

The agent runs emuly link on the machine that can reach the server. This rule also covers an agent that runs on a remote VM.

3. Route A: SSH tunnel with gh

Route A is the default when gh is installed and logged in.

emuly link does two things for Route A:

  1. It runs gh codespace ssh -c <name> -- -N -R 3000:127.0.0.1:3000.
  2. It calls POST /v1/phones/{id}/links. The runner then runs adb reverse tcp:3000 tcp:3000.

The traffic does not go through the Emuly control plane. GitHub checks the login of the user.

Not tested: that gh codespace ssh accepts the -R flag. The file native-adb.md already uses -L the same way. Step 0 of the build tests this.

4. Route B: relay, when gh is not installed

Route B needs only the Emuly key and Node 22 or later. It needs no gh and no GitHub login on the laptop.

How Route B works:

  1. emuly link gets a one-use ticket with the Emuly key. The video stream uses the same ticket method today.
  2. emuly link opens one websocket to the control plane.
  3. The control plane relays the websocket to the runner. It uses the connection to the runner that it has today.
  4. The runner listens on 127.0.0.1:3000 in the codespace and runs adb reverse.
  5. Each TCP connection from the app becomes one numbered stream in the websocket.

Route B costs more than Route A. The traffic uses the Emuly server. Use Route B only when Route A is not available.

5. Guide for the agent: which route to use

emuly link selects the route. The agent does not select it. The skill gives the same steps for an agent that must do them by hand.

CheckResultAction
gh auth statusLogged inUse Route A.
gh auth statusInstalled, not logged inUse Route B. Tell the user that gh auth login -s codespace makes links faster.
gh auth statusLogged in, no codespace scopeUse Route B. Tell the user about gh auth refresh -h github.com -s codespace.
gh --versionNot installedUse Route B. Do not install gh.
node --versionNode is older than 22, and gh is not installedAsk the user to permit one install. See below.

When neither route is available

The agent asks the user one question: "Can I install the GitHub CLI?" The agent installs nothing before the user says yes.

  1. Windows: winget install --id GitHub.cli
  2. macOS: brew install gh
  3. Linux: follow https://github.com/cli/cli/blob/trunk/docs/install_linux.md
  4. Run gh auth login --web -s codespace. The user approves one time in the browser.
  5. Run emuly link again. It now uses Route A.

The GitHub account in gh must be the account that owns the codespace. If it is not, emuly link uses Route B and prints the reason.

6. How the agent detects the problem

  1. Before install. The agent searches the app config for localhost, 10.0.2.2, 192.168., and .ts.net.
  2. After a failure. The agent calls GET /v1/phones/{id}/net-check?target=host:port. The runner tests the connection from inside the emulator. The reply gives the class of the address and the exact fix.
  3. During the run. The app-events route reports connection errors from logcat, such as ECONNREFUSED and UnknownHostException, with the same fix text.

Example reply from net-check:

{ "reachable": false, "class": "laptop-loopback",
  "fix": "emuly link <phone> 3000" }

One limit: the app must call localhost or 10.0.2.2, not the real hostname. The agent changes the dev config of the app when the app uses a real hostname.

7. Efficiency

  • No link when no link is necessary. Public servers and servers in the codespace use the direct path.
  • One process for all ports. emuly link <phone> 3000 8081 uses one SSH session, or one websocket.
  • No new handshake for each request. Each TCP connection is one stream inside the open tunnel.
  • No work while idle. There is no polling. net-check runs only when the agent calls it.
  • No inspection of data. The tunnel copies bytes. It does not parse or encrypt them a second time.

For the agent: one command starts a link. The command prints one line of JSON with the route and the ports.

A link stops when the phone stops. The runner applies adb reverse again after an emulator restart.

8. Security

  1. Each end binds to loopback only. The codespace port never becomes public.
  2. A link opens one port. It does not open the full network of the laptop.
  3. The agent asks the user before it links a target that is not localhost. The agent also asks for database ports.
  4. GET /v1/phones/{id}/links lists each open link. The web app shows the same list.
  5. Route B uses a one-use ticket. The Emuly key is not in the websocket URL.

One risk stays: each app on the phone can reach a linked port. Narrow ports keep this risk small.

9. Options that this plan rejects

OptionWhy not
Tailscale inside the codespaceEach codespace becomes a temporary device in the Tailscale console. The console fills with old devices. It also needs an auth key from the user.
A SOCKS proxy for the full networkIt opens the full network of the laptop to each app on the phone.
A public codespace portIt puts the port on the internet.
A third-party tunnel such as ngrokIt puts the server of the user on the internet. It needs one more account.
